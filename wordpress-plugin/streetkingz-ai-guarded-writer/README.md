# Street Kingz AI Guarded Writer

v0.1.10 retains the protected-route cache controls and replaces Elementor's whole-document save with a fixed-purpose, two-leaf raw patch. The writer starts from the freshly guarded raw template-2003 `_elementor_data`, locates only `c80e718.settings.editor` and `40869c27.settings.editor` through unique raw/parsed anchors, replaces only their JSON string tokens, and rejects any candidate whose strict parsed structure differs anywhere else. It then persists the exact candidate through the fixed post-2003 `_elementor_data` coordinates. No caller can supply a post ID, meta key, widget ID, or arbitrary value.

This deliberate exception to Elementor's document API avoids reserialising unrelated historical template settings. It is narrower than a generic metadata editor: the template, meta key, widgets, values, approval, current-state hashes, and execution contract are all independently fixed or validated. Persisted raw bytes and strict parsed state—not the metadata function return—decide success. Rollback restores the exact pre-write raw string and verifies its byte hash and parsed structure after clearing bounded caches.

This plugin is deliberately bound to the explicit product 70/template 2003 approval packaged with it. It accepts no copy, product IDs, template IDs, widget IDs, fields, metadata or publication state from callers.

It creates the dedicated `streetkingz_ai_writer` role with exactly WordPress `read` plus `streetkingz_ai_write_approved_product_copy`. The role is never assigned to a user automatically, and the existing authoritative GET reader remains independent. `read` permits ordinary authenticated identity/Application Password use; it does not grant post, product, page, media, WooCommerce, plugin, theme, publication or administration rights.

Fresh activation creates the role. A versioned `init` migration also creates or reconciles it when an already-active v0.1.3 plugin is replaced, because WordPress does not rerun activation hooks in that case. The migration touches only this named role and stores its migration version; it never finds or modifies users. Deactivation and uninstall deliberately leave the role and user assignments intact to avoid surprise lockouts or account changes.

The dry-run and execute routes share all approval/current-state checks. v0.1.7 stores only two validated runtime control records in fixed, non-autoloaded WordPress options: one active approval and one active execution contract. Narrow Writer-only REST operations install, inspect, and explicitly remove those exact manifest types. They accept no arbitrary option names, files, products, templates, operations, copy targets, or credentials. Bundled JSON fallback has been removed, leaving one deterministic source of truth.

Approval and execution-contract installation perform no content writes and do not claim an execution ID. Execute remains locked until the active contract matches the active approval fingerprint, current-state hashes, approved-target hashes, fixed product/template identity, exact four-operation set, publication lock, explicit execute mode, and an unused high-entropy one-time execution ID. Active records cannot be silently replaced. Manifest lifecycle events are stored separately from permanent execution-claim history.

Immediately before the first mutation, the plugin atomically claims a SHA-256-derived option name using one `INSERT IGNORE` against WordPress's persistent options table and its unique `option_name` constraint. Exactly one concurrent request can insert the claim. Claimed IDs are never deleted or made reusable. Their audit state advances from `claimed_executing` to either `succeeded` or `failed_after_claim`; failure to persist a final state still leaves the original claim permanently replay-blocked.

Execute additionally requires successful immutable rollback persistence before either write. Product writes contain only `ID`, `post_title`, and `post_excerpt`; the fixed template write changes only the two approved editor string tokens. Deployment and capability assignment remain separate from explicit live-write authorisation.

The dedicated role remains free of generic post, product, page, Elementor-library, metadata, or administration permissions. Rollback verification clears bounded WordPress and LiteSpeed caches and freshly reads persisted database state; a false persistence return with exact target bytes is accepted, while a truthy return with incorrect bytes is rejected and rolled back.
